# Production-like deployment on a VPS (k3s)

Same Helm chart as local. Only **values** change (`charts/platform/values-prod.yaml`);
no template is edited. This page is the runbook.

## What changes between local and VPS, and why

| Concern | Local (`values-local.yaml`) | VPS (`values-prod.yaml`) | Why no template changes |
|---|---|---|---|
| Domains | `store.localtest.me`, `dashboard.localtest.me` (resolve to 127.0.0.1) | `store.<IP>.nip.io` / your own domain | Hosts are `store.host` / `gateway.host` values used by the Ingress templates |
| TLS | off (plain http) | `ingress.tls.enabled: true` + cert-manager `clusterIssuer` | The Ingress template adds `tls:` and the cert-manager annotation only when enabled; cookies become `Secure` automatically |
| Ingress controller | Traefik (k3d) | Traefik (k3s ships it) | `ingress.className` value; NetworkPolicies read the controller's namespace/labels from values |
| Storage | cluster default (local-path) | `global.storageClass: local-path`, bigger sizes | PVC templates read `storageClass` and sizes from values |
| Images | built locally, `k3d image import` | pushed to a registry, `global.imageRegistry: ghcr.io/<you>` | The image helper prefixes our images with the registry value |
| Secrets | generated by Helm on first install, kept on upgrade (`lookup`) | created **before** install with `k8s/create-secrets.sh`; `secrets.generate: false` | Same Secret names/keys either way; templates only reference them |
| LLM | Ollama on the laptop (`host.docker.internal`) | Groq (or Gemini) with `llm.existingSecret` | URL/model/secret name are values |
| Gateway egress | Ollama's port on Docker Desktop's host network | HTTPS to public IPs only | `gateway.extraEgress` is appended to the NetworkPolicy |
| Replicas | 1 gateway | 2 gateways | `/mcp` is stateless; state lives in Postgres |

## 1. Server

Any small VPS works (2 vCPU, 4 GB RAM is comfortable). Ubuntu 24.04 shown.

```bash
# on the VPS
curl -sfL https://get.k3s.io | sh -               # k3s: Kubernetes + Traefik + local-path storage
sudo cat /etc/rancher/k3s/k3s.yaml                # kubeconfig: copy it to your laptop
```

On your laptop, save that file as `~/.kube/k3s-vps.yaml`, replace `127.0.0.1` with the
VPS IP, and `export KUBECONFIG=~/.kube/k3s-vps.yaml`. Open ports 80 and 443 (and 6443
only from your own IP) in the VPS firewall.

k3s enforces NetworkPolicies out of the box (kube-router), so the policies in the chart
work unchanged.

## 2. DNS

Either a real domain with two A records (`store.example.com`, `dashboard.example.com`
→ VPS IP), or no domain at all: `store.203.0.113.10.nip.io` resolves to `203.0.113.10`.
Put the hosts into `values-prod.yaml` (`store.host`, `gateway.host`).

## 3. Images

The VPS can't see images built on your laptop, so push them to a registry
(GitHub Container Registry shown; tags must match `values.yaml`):

```bash
echo $GITHUB_TOKEN | docker login ghcr.io -u YOUR_GITHUB_USER --password-stdin
for pair in mcp-woocommerce:0.1.1:mcp-woocommerce mcp-notes:0.1.1:mcp-notes \
            mcp-toolbox:0.1.1:mcp-toolbox mcp-gateway:0.3.0:gateway mcp-dashboard:0.1.0:dashboard; do
  IFS=: read name tag dir <<< "$pair"
  docker build -t ghcr.io/YOUR_GITHUB_USER/$name:$tag $dir
  docker push ghcr.io/YOUR_GITHUB_USER/$name:$tag
done
```

Make the packages public on GitHub, or create a pull secret and list it in
`global.imagePullSecrets`.

## 4. TLS with cert-manager (optional)

```bash
helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true
kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: letsencrypt-prod }
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: you@example.com
    privateKeySecretRef: { name: letsencrypt-prod }
    solvers:
      - http01: { ingress: { ingressClassName: traefik } }
EOF
```

Shared domains like nip.io often hit Let's Encrypt rate limits; with a real domain this
is reliable. Without TLS, set `ingress.tls.enabled: false`.

## 5. Secrets (before installing)

```bash
bash k8s/create-secrets.sh            # namespaces + all platform Secrets, random values
kubectl -n gateway create secret generic llm-api-key --from-literal=api-key=gsk_...   # Groq key
```

Nothing secret is in git or in a values file. `create-secrets.sh` never overwrites an
existing Secret (database passwords must not change after first use).

## 6. Install / upgrade / roll back

```bash
helm upgrade --install platform charts/platform -f charts/platform/values-prod.yaml --timeout 15m --wait
helm history platform
```

Upgrading a component = bump its image tag (in values or `--set gateway.image.tag=0.3.1`)
and run the same `helm upgrade`. Kubernetes replaces pods one by one (`RollingUpdate`;
WordPress uses `Recreate` because of its single-node volume) and the store-setup hook
re-runs idempotently (e.g. installs a new pinned WooCommerce version and runs its DB update).

Rolling back = `helm rollback platform <REVISION>`: Helm re-applies the old manifests
(old image tags, old config). Note what it does NOT roll back: data in volumes. A
WooCommerce or database schema upgrade is one-way, so take a backup first
(`kubectl -n store exec mysql-0 -- mysqldump ...`, `kubectl -n gateway exec postgres-0 -- pg_dump ...`).
